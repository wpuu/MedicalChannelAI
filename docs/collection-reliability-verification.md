# 采集、发布与展示可靠性验收

> 以下历史测试数字绑定 `3af6db8` 及此前修复，不是新候选测试数。2026-10-03 双时段候选、缺失原85项证据、独立审查、当前生产和发布/回退门禁见 [受控恢复清单](ops/twice-daily-release-20261003.md)。本轮未重新运行历史浏览器矩阵。

代码验收只用离线数据、HTTP 替身和内存缓存，不启动生产采集，不改工作流文件、DNS、部署或数据库结构。另按用户此前确认的暂停结论操作 GitHub 控制面；线上观察只读公开状态和快照，不调用采集入口或写缓存探针的健康端点。

## 时间与结果的含义

- 来源扫描成功不等于全量刷新成功。零候选、范围过滤后零候选、同来源部分详情成功保留各采集器原有政策。
- 地区有选中候选但详情全部失败，或该地区的发现查询全部失败时，阻止发布；其他地区成功和历史记录不能掩盖失败。
- `snapshot_as_of` 表示已接受的发布版本时间。增量空扫描和仅观察时间改变的重验不产生新版本；成功完成全部必需来源门禁的全量周期可以发布新的完整覆盖证明，即使事实内容未改变。
- `collection_coverage.complete=true` 表示当前全量周期所有配置必需来源通过门禁，并非官方数据穷尽覆盖。此时 `last_complete_as_of` 等于版本时间。
- 健康来源带来实际变化，可以发布部分覆盖版本；其 `complete=false`，保留上次已证明的完整覆盖时间，无此证明时为 `null`。已知失败不能因新周期重置而消失。
- 已有发布版本而 canonical 分片丢失时，不能用旧本地种子替代未知历史后发布。应保留已发布版本并报告恢复前置条件；健康来源仍可继续扫描、保存已核验内容。
- 旧快照缺少覆盖信息时，完整覆盖状态为未知。页面根据实际正在显示的版本、来源、覆盖信息判断新鲜度；部分覆盖和未知状态不放行页面自动化。
- 生产 pipeline 健康检查要求有效完整覆盖和完成的采集状态。数据库状态查询失败或降级时，旧缓存不能恢复为健康；未知覆盖、异常时钟、部分覆盖和失败周期都有稳定原因码。时间门限沿用状态接口的 30 小时与 15 分钟未来偏差；此检查不作为独立来源采集的启动门禁。
- AI 缓存及单条、批量响应必须与输入卡片的快照版本、来源及 runtime origin 一致，本地缓存使用该卡片的版本。应用迟到结果时还需核对当前商机 ID 和版本，不能把旧建议挂到已刷新卡片或使详情倒退。已有 READY 建议也保留降级提示；AI 已配置与当前允许分析分别显示。
- 浏览器先按实际请求及重定向后的 origin 判断快照来源；跨域快照不能凭 `DATABASE` 响应头冒充页面服务端的数据库版本。同源 API 代理返回的真实数据库、运行缓存、内置或远程来源保留原语义。
- 服务端 AI 对显式部分覆盖版本返回 `409 VERIFIED_SNAPSHOT_COVERAGE_INCOMPLETE`。缺少覆盖信息的旧版本保留原有服务端策略；本轮没有把 public AI core 的历史时钟政策统一为 private/prewarm 的 30 小时门禁。

## 可重复的离线验证

在 `web/pipeline` 执行 `python3 -m unittest discover -s tests -v`，验证采集、队列、发布与文件保护回归。在 `web` 执行 `npm run build`，运行同一 Python 测试集、Node 行为验证、TypeScript 检查和 Vite 构建。

构建前置任务会重新生成 bundled snapshot。需要保留工作区原字节时，应在临时副本运行构建，并比较原工作区文件哈希。不要为开发验证触发远端工作流、生产采集或反复部署。

Node 行为验证的网络与数据库调用必须使用替身；检查失败不得改用生产服务。`node scripts/check-partial-coverage-ai.mjs` 可单独验证单条、批量、缓存读取和预热的部分覆盖门禁。
