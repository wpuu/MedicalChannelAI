# AI 商机发现：Agnes 影子挖掘与基准验证

## 目的

MedicalChannelAI 不把人工搜索到的商机直接做成产品数据。人工/确定性适配器已经核验过的样本只作为 **gold benchmark（已知答案）**，用于判断 AI 是否真的具备自主发现能力。

生产方向是：

1. 实时雷达由用户维护医院/机构和公开渠道，不维护人工挑出的具体商机，也不预置医院生产清单；
2. Agnes 从本次真实抓取到的官方链接集合中自主挑出可能属于采购前期窗口的候选；
3. 模型只能引用输入中真实存在的 URL，编造 URL 会被程序拒绝；
4. AI 输出统一标记 `DISCOVERED_UNVERIFIED`，不能直接进入公开事实层；
5. 将 AI 发现结果与现有独立 VERIFIED 集合比较，计算“已知样本发现能力分”；
6. Agnes 找到而旧适配器没有找到的链接属于“新候选”，必须再走独立官方事实核验，验证通过后才能发布。

这意味着人工搜索的作用被限制在**测试和验收**，而不是成为未来数据生产方式。

## 实时雷达的医院与渠道管理

实时 `/radar` 的新工作区默认扫描范围为空。用户可以：

- 单个增加医院官网、政府采购、公共资源交易、卫健主管部门等公开入口；
- 修改、停用、重新启用、删除渠道；
- 批量导入 `医院/机构名称 | https://官方栏目地址`；
- 同一个医院配置多个真实公开入口；
- 把跨医院的政府采购/公共资源渠道作为独立入口加入。

离线 benchmark 仍保留固定测试入口，只为了让同一套能力测试可以重复执行。**benchmark 的固定测试入口不决定实时产品扫描哪些医院。**

## 扫描缓存：先检查官网，再决定是否调用 Agnes

每次点击“检查更新”都会先重新读取公开页面，并对本次真实官方链接集合计算内容指纹：

- 指纹未变化：复用已保存的上次 AI 结果，**不重复调用 Agnes**；
- 指纹变化：重新调用 Agnes；
- 用户修改渠道 URL/类型：旧扫描结果和该渠道历史发现自动失效；
- 用户也可以显式“强制 AI 重分析”；
- 服务端会重新校验缓存候选是否仍属于本次真实官方链接集合，不能靠浏览器缓存绕过 URL grounding。

## 发现历史：新扫描不覆盖旧机会

只保存“最近一次扫描结果”仍然不够，因为官网列表滚动以后，旧候选会离开当前页面。实时雷达因此另有累计发现账本：

- 以 `source_id + 官方URL` 去重；
- 保存首次发现时间、最后出现时间、累计命中次数；
- 标记“最近扫描仍可见”或“历史已保存”；
- 新一轮扫描不会覆盖已经发现的历史机会；
- 删除/修改渠道时，同渠道历史按用户操作一起清理，避免把错误渠道留下的结果继续混入工作区。

演示版先把渠道、最近扫描结果、累计发现和渠道健康统计保存在当前浏览器。Pilot 账号数据库接入后再迁移到账号级持久化，不改变“先检查公开页面变化、再决定是否调用 AI”的逻辑。

## 公开数据源优化机制

每个渠道累计：

- 检查次数；
- AI 实际调用次数；
- 缓存复用次数；
- 候选/新候选数量；
- 连续失败次数；
- 连续无候选次数。

当前第一版规则：

- 连续失败 >=2 次：标记“建议检查”；
- 连续无候选 >=3 次：标记“连续低产出”；
- 不自动删除渠道，避免把暂时没有项目的真实官方栏目误判成无效；
- 由用户决定停用、删除或替换。

真实运行数据积累后，下一层质量分可以加入：独立核验通过率、有效新候选率、重复率、提前发现天数、错误率。这样渠道不是“越多越好”，而是不断淘汰低价值/错误入口，补充高价值入口。

## 公开 URL 安全边界

因为实时雷达允许用户填写公开渠道 URL，服务端必须防止把它变成任意网络请求工具：

- 只接受 HTTPS；
- 拒绝 localhost、直接 IP、内网/保留地址解析结果；
- 跳转只允许同一官方主机的 `www`/非 `www` 变体；
- 限制页面体积和跳转次数；
- 候选链接仍必须来自本次实际抓到的同域官方链接集合。

## 当前基准分

`run_agnes_discovery_benchmark.py` 的发现能力分只评价 AI 商机挖掘器，不冒充整个产品评分：

- 75%：对独立 VERIFIED 已知样本的召回率；
- 20%：URL grounding，模型是否只使用真实官方候选链接；
- 5%：结构化响应有效率。

**召回率分母必须与本次 AI 真正看见的官方链接集合一致。** 历史 VERIFIED 记录如果已经离开当前官网列表、位于未抓取分页，或超出实时雷达本次 80 条分析上限，只保留为历史参考，不能拿来压低本次发现分。实时雷达的范围是 `CURRENT_ANALYZED_OFFICIAL_LINKS`；离线 benchmark 的范围是 `CURRENT_FETCHED_OFFICIAL_LINKS`。

建议第一阶段门槛：

- 当前可见已知样本召回率 >= 85%；
- URL grounding >= 99%；
- 发现能力分 >= 85；
- 编造 URL 必须被程序 100% 拒绝；
- 新候选在独立核验通过前，永远不能作为“官方已验证商机”展示。

## 对老杨演示版的含义

演示不依赖预先塞入的医院或商机。现场可以先添加老杨真正想看的医院/渠道，再执行：

**用户指定真实医院/渠道 -> 系统检查公开页面是否更新 -> Agnes 只在有新内容时分析 -> 保存发现历史 -> 官方证据核验 -> 结合客户产品/医院关系重排 -> 一键生成今天应该怎么跟。**

只有候选实际来自 AI 挖掘并通过独立核验，UI 才允许把它当成已核验商机。这样演示逻辑和未来正式产品逻辑一致。

## 离线能力测试

仍可手工触发 GitHub Actions 工作流：`Agnes Discovery Shadow Benchmark`。工作流只读仓库、调用 Agnes、输出 benchmark artifact；**不会修改 Production 数据，不会把 AI 候选自动写进公开快照。**

需要 GitHub Actions Secret：`AGNES_API_KEYS`。如果未配置，工作流直接失败，不能生成伪造评分。
