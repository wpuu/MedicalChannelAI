## 1. 产品范围与判断顺序

首轮验证限天津、一个明确产品细分和少量真实渠道客户。三个 Persona 只是离线测试画像；不代表同时交付全部细分、全国覆盖、竞争情报、政策或监管提醒。

每条推荐分别判断，不能用一个总分替代：

1. **事实与来源**：官方原文核验成功，关键字段有证据；第三方只能提供发现线索。
2. **相关性**：具体客户产品与具体采购子项/包件是否直接匹配。仅父类别接近为待确认，不能冒充直接匹配。
3. **资格**：公告硬要求与客户确认材料分别记录；结果为满足、不满足或未知。产品相关不代表具备入围、授权、经营或注册资格。
4. **窗口**：以固定判断时钟和官方窗口计算；新发现与已参与项目分别判断。报名结束不因开标未到自动恢复新进入机会。
5. **动作**：明确核实资格、准备、报名/提交、持续跟踪等动作。资格未知可以提示核实，不能写成具备资格或可投；不匹配、不满足或无有效动作时允许零推荐。

相关性、资格、窗口和动作须保留各自结果及理由证据。模型只选择服务端允许的枚举、已有产品/子项 ID 和证据引用，不创造日期、资质、产品、关系、预算或胜率。相关性门禁、资格模型和交付流程均为后续能力，**不在本轮 P0 实现范围**。

## 2. 项目、公告与回放身份

- 项目身份与公告事件身份分离；产品相同不是项目相同。同项目关联须有采购主体、项目/包号或官方交叉引用等证据；无证据只记可能关联，不能合并。
- 意向、调研、正式采购、中标等是项目阶段；更正、延期、终止等是公告事件，不能单凭更正公告覆盖真实项目阶段。
- 每个可执行案例固定 `as_of`（含时区）、画像版本、跟进状态、官方详情/附件的当时版本及哈希、预期结果。回放不能使用该时点尚未出现的公告或后续结果。
- Gold Set 15 例仅为人工规则冒烟集。未封存官方详情/附件、未补齐明确时钟或资格条件的案例，不得计入自动验收通过率。

## 3. P0 数据提交与故障边界

- `tjzyefy`、`tjzyefy_intent`、`tjzxfc` 接入现有 runtime 显式来源集，复用官方 discovery/detail adapter；各自独立 canonical 状态、bootstrap、pending 和健康状态。
- **单源 fail closed**：某源核验失败、未完成或存在未解决 pending 时，不发布该源的部分新事实，不抹去最后已验证状态。可独立完成的其他源继续执行；降级覆盖必须明确，不能把局部刷新解释成全部来源健康。
- pending/barrier 仅在对应 URL 已被 verified canonical 覆盖、已明确核验为 non-fact，或有其他明确可审计解除依据时清理；清理其他成功 URL 不能顺带抹去未解决 URL。
- 日内调度有独立于一次长任务成败的兜底；过期 `RUNNING` 不得永久阻塞后续扫描；重试、恢复和旧 cycle 均受租约/身份及有界成本约束。
- 快照的结构、官方事实边界、时间、大小、版本/单调性等校验须在权威持久化之前完成。权威写入只提交一次；失败不能留下可被后续读取视为成功的新版本。
- “已提交”指通过验证且完成权威写入确认/读回的版本；尝试时间、正在运行或暂存输出不等于已提交。状态不得报告尚未提交的刷新成功。
- 每源健康至少可区分最近尝试、最近完整成功、最近已提交数据、失败原因和过期状态；快照生成时间不能替代每源新鲜度。没有新公告但成功扫描仍是有效成功，源长期无更新不应被别源刷新掩盖。
- 空的**已验证完整机会池**是合法结果；不能用旧 `cards` 回填。空池下已有提醒仍应能 ACK，且只清提醒，不改变销售状态。
- 公开 AI 在服务器执行 30 小时快照新鲜度门禁；无有效快照、未来异常时间或超龄时拒绝分析，不能依赖前端按钮禁用。源级降级必须可观察，整体时钟不能证明各源均健康。
- EdgeOne 代理始终请求固定可信 origin；路径、重定向或客户端头不能把用户 Cookie/Authorization 带往其他主机。
