# 目标医院与医院关系：独立建模

## 结论

`目标医院（target hospital）` 与 `医院关系（hospital relationship）` 必须是两个独立维度。

- 目标医院回答：**我想不想持续关注这家医院？**
- 医院关系回答：**我在这家医院是否存在已经确认的业务关系？关系到什么科室、强度如何？**

二者不能互相推导。

## 必须支持的四种现实状态

| 目标医院 | 已有关系 | 含义 |
|---|---|---|
| 是 | 是 | 重点经营医院，并且已有关系 |
| 是 | 否 | 想开发/进入/长期关注，但目前没有关系 |
| 否 | 是 | 历史或现有关系存在，但当前不是重点开发对象 |
| 否 | 否 | 普通公开机会，按产品、时机等其他条件判断 |

因此，“没有关系但关注医院”是正常且重要的状态，不能用 `NONE/UNKNOWN relationship` 冒充目标医院。

## 产品语义

### 目标医院

建议字段：

- `hospital`：医院/采购单位
- `department`：可选；留空表示全院
- 后续可扩展：关注原因、关注等级、负责人、开始关注时间、提醒策略

目标医院主要用于：

1. 重点医院动态列表；
2. 新需求/调研/采购意向提醒；
3. AI 分析时明确“这是用户主动关注对象”；
4. 后续区域/医院雷达自动建立扫描任务；
5. 单独统计目标医院覆盖率与机会产出。

### 医院关系

继续只表达已经确认的关系事实：

- `hospital`
- `department`
- `relationship_strength`
- 后续可扩展负责人、最近确认时间、关系来源等

## 排序原则

第一阶段：**目标医院不计入 `RELATIONSHIP` 分数。**

原因：用户主动关注某医院，不等于在该医院有关系。把“关注”算作关系分，会让优先级看起来更高但事实基础是假的。

当前 `RELATIONSHIP` 仍只由已确认关系产生。

目标医院先作为独立的 `focus/watch` 信号，用于标签、筛选、提醒和 AI 上下文。等真实 Pilot 有数据后，再决定是否增加独立的 `STRATEGIC_FOCUS` 排序分量，而不是污染关系分。

## 数据边界

Real Pilot 使用独立私有数据结构保存目标医院，不写入公开事实层，也不从公开联系人、招标联系人或医院官网自动推断用户关系。

目标医院可以与医院关系同时存在；删除目标关注不能删除医院关系，删除医院关系也不能自动取消目标关注。
