# AI 情报雷达：区域增量搜索与本地保存边界

更新时间：2026-09-02

## 1. 区域大范围搜索的定义

“天津市”不应实现成一次性把关键词交给搜索引擎或 AI 的黑盒搜索。

真实产品把区域定义为**用户维护的一组公开官方渠道**：医院官网、政府采购、公共资源交易、卫健主管部门以及其他官方入口。一个区域可以有很多渠道，一个医院也可以有多个栏目。区域扫描逐渠道执行，来源可以持续增加、停用、替换和删除。

这样做的原因：

- 搜索引擎索引不保证及时和完整；
- AI 不能替代真实公开页面；
- 官方栏目可以建立明确的检查游标、失败率和产出率；
- 后续可以依据真实运行指标优化渠道组合，而不是依赖人工记忆。

当前通用实时雷达单个入口只读取当前页，并最多分析 80 个官方链接。需要分页的官网应先把分页/栏目作为独立入口；正式扩大覆盖时应为高价值站点增加专用分页适配器，不能猜分页规则。

## 2. 增量搜索

每次检查必须重新访问官方列表页，否则无法知道是否出现更新。但是 AI 不应重复判断旧链接。

v0.3 保存每个来源上一次的 `anchor_snapshot`：

- URL 新出现：`new_anchor_count`；
- URL 相同但标题变化：`changed_anchor_count`；
- 上次存在、本次离开当前窗口：`removed_anchor_count`；
- URL 与标题均未变化：`reused_anchor_count`。

处理规则：

1. 当前链接集合完全未变化：不调用 AI；
2. 只有排序变化或旧链接移出、没有新/变更链接：不调用 AI；
3. 出现新增/标题变化：只把这些增量链接发给 Agnes；
4. 未变化链接沿用上一轮判断；
5. 当前候选与历史发现分离，滚出列表的旧机会仍保留在发现账本；
6. 用户仍可显式强制全量 AI 重分析。

因此，“不重复搜索”准确指**不重复 AI 判断旧链接**，而不是停止访问官网。停止访问官网会直接导致漏更新。

## 3. 本地保存容量

原来的 `localStorage` 不适合作为大范围长期发现账本：容量通常很小，而且整个读写是同步的。渠道数、链接快照和累计发现增长后存在触顶和卡顿风险。

当前演示版改成：

- 重数据优先写入浏览器 `IndexedDB`；
- `localStorage` 只保留轻量启动信息；
- IndexedDB 不可用时才降级回 localStorage；
- 使用 `navigator.storage.estimate()` 展示浏览器给当前站点的实际用量/额度；
- 支持请求浏览器 persistent storage，降低在存储压力下被自动清理的概率；
- 工作区估算达到 25 MB 或站点存储占用达到额度约 75% 时提示尽快迁云。

IndexedDB 的可用额度由浏览器、设备和剩余磁盘决定，不能写死成固定容量。它足够支撑 Preview/演示阶段的大量本地数据，但仍不是 Real Pilot 的最终持久化方案。

本地数据仍可能因为以下原因丢失：清除网站数据、隐私/无痕模式、浏览器策略、设备故障、浏览器存储回收。它也不能解决跨设备同步或网页关闭后的后台扫描。

## 4. 云端迁移触发条件

以下任一出现，就不应继续把本地存储当主方案：

- 需要跨手机/电脑同步；
- 需要浏览器关闭后继续定时扫描；
- 发现账本不可接受丢失；
- 单用户维护大量区域/渠道并持续数月；
- 需要团队共享；
- 需要服务端做长期渠道质量统计和自动优化。

Real Pilot 将把来源、链接游标、发现历史、渠道健康度和扫描任务迁到账号级数据库；浏览器仅做缓存和展示。
